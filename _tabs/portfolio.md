### 여행파티

**2023.06 ~ 2023.12** · 백엔드 · 인프라
`Spring Boot` `MySQL` `AWS` `Kafka` `STOMP` `Jenkins`

여행 동행 매칭 애플리케이션입니다.

배낭여행처럼 혼자 다니는 여행이 젊은 층에서 늘고 있습니다. 유럽 배낭여행 정보 카페 '유랑'만 해도
222만 명이 가입되어 있고 많은 사람들이 동행을 구합니다. 하지만 익명에 가려져 동행을 구하다 보니
불만 있는 글이 쉽게 눈에 띄고, 성향이 맞지 않아 불편해지는 경우가 나옵니다.
이런 점을 최대한 보완해보는 것이 프로젝트의 목적이었습니다.

개발자 3명(FE 1, BE 2)으로 진행했고, BE 담당자 중 한 명인 제가 인프라를 함께 맡았습니다.

#### AWS 인프라 구축

- ALB와 Bastion 서버를 제외한 **모든 서버를 private subnet에 배치**했습니다.
- ALB에서 HTTPS 인증을 받고 nginx로 로드 밸런싱하도록 설정했습니다. nginx에서는 WAS로 보낼 영역을 구분해 NLB로 보냅니다.
- nginx만으로도 WAS 로드 밸런싱이 가능했지만, NLB가 성능이 더 뛰어나고 추가 설정 없이 로드 밸런싱을 할 수 있다는 이점 때문에 NLB를 택했습니다. 포트를 기준으로 API 서버와 Chat 서버를 나눠 리스너를 등록했습니다.
- 장애 대처를 위해 **AZ를 최소 2개 이상** 사용하고, NLB가 각 AZ를 돌아가며 볼 수 있게 구성했습니다.
- 각 인스턴스를 도커 이미지로 굴리는 것이 목적이라 오케스트레이션은 ECS, 레포지토리는 ECR로 결정했습니다.

#### 채팅 서버 — 웹소켓에서 Kafka까지

카카오톡 같은 실시간 채팅을 만드는 것이 목표였습니다. 처음에는 웹소켓으로 시작했다가,
**STOMP로 pub/sub 구조**를 만들고 메시지 규약을 정하는 편이 FE와 BE 양쪽에 편하다고 판단해 바꿨습니다.

그런데 개발 서버(AWS)에 올려 테스트하니 **될 때가 있고 안 될 때가 있었습니다.**

원인은 명확했습니다. 채팅 서버가 두 대 돌아가고 라운드 로빈으로 분산되니, A 서버에 연결을 등록하고
다음 요청이 B 서버로 가면 각 연결 정보가 자기 서버에만 있어 통신이 될 리가 없었습니다.

두 가지 방법을 놓고 고민했습니다.

**1. 웹소켓 세션 정보를 DB에 저장**
: 간단하게 해결됩니다. 빠르고 캐싱에 쓰이는 Redis에 연결 정보를 저장했다 불러오는 방식입니다.
다만 성능을 확답하기 어려웠고, Redis가 터지면 세션 정보가 전부 날아가는 게 맞나 하는 고민이 들었습니다.

**2. 외부 메시지 브로커 사용**
: Kafka, RabbitMQ, Redis 중에서 골라야 했습니다. 프로젝트가 아주 잘 된다는 가정하에 성능을 알아보니
Kafka와 Redis가 선호되었습니다. 또 추후 숙소 구매 대행을 카카오톡 정산처럼 만들 예정이라 안전성이 필요했습니다.
**최종적으로 Kafka**를 선택했습니다.

동작은 이렇습니다.

1. STOMP의 sub 주소에 연결합니다 (채팅방 접속)
2. 메시지를 보내면 Kafka Producer가 해당 메시지를 topic에 보냅니다
3. Kafka Consumer가 메시지를 읽고 roomId를 기반으로 주소를 만들어 보냅니다
4. 그 주소를 구독하고 있는 대상이 메시지를 읽습니다

로컬 테스트를 마치고 개발 서버에 올리니 **같은 증상이 다시 났습니다.**
원인은 서버마다 KafkaListener에 **같은 groupId**를 넣은 것이었습니다. 두 서버가 같은 group에 묶이면
메시지를 한 번에 처리하지 않을까 생각했는데, 실제로는 한쪽 서버가 메시지를 보내기는 하지만 받지는 못했습니다.

**다중 컨슈머 그룹**으로 해결했습니다. `random.uuid`를 groupId에 넣어 인스턴스마다 고유한 값을 갖게 하고,
topic은 같은 것을 바라보게 했습니다. A가 읽고 있을 때 B도 읽을 수 있는 구조입니다.
그 결과 외부 메시지 브로커로서 제 역할을 하게 되었습니다.

#### 토큰 기반 인증 처리

- access 토큰만 쓰기에는 보안 이슈가 있어 **refresh 토큰을 함께** 쓰기로 했습니다. 둘 다 쿠키에 담아 전달합니다.
- refresh 토큰은 in-memory인 **Redis에 저장**해 검증을 빠르게 했고, 유효 기간에 맞는 **TTL**을 넣어 관리했습니다.
- refresh 토큰을 쓰더라도 탈취당했을 때의 보안 이슈가 남아, **호출할 때마다 새로 발급**하도록 했습니다. 탈취당해도 최대 한 번만 쓸 수 있습니다.
- Express에서는 인증 절차를 전부 middleware로 처리했지만, NestJS에서는 역할을 분리해 **Guard**에서 처리하도록 했습니다.

#### 이메일 인증 처리

회원가입과 비밀번호 찾기에 이메일 인증을 사용했습니다. `@nestjs-modules/mailer`와 네이버 아이디로 구현했습니다.

1. 서버가 임의의 6자리 코드를 만들고 암호화합니다
2. 암호화한 값은 쿠키로, 코드는 response로 클라이언트에 전달합니다
3. 클라이언트가 코드를 입력해 요청을 보내면, 쿠키의 값과 코드를 서버에 저장된 salt로 비교해 인증합니다

#### 로깅

`nestjs-winston`과 `winston-daily-rotate-file`로 로깅을 담당했습니다.

- 처음에는 예외 처리가 각 서비스와 컨트롤러에 흩어져 있어 로그를 일일이 넣어야 했습니다. NestJS의 **exception filter**를 써서 예외 발생 시 필터가 로그를 남기도록 바꿨습니다.
- production 환경에서는 성능을 위해 console 출력을 하지 않고 file에 error와 warn만 남기도록 했습니다.
- 기존 방식에서는 warn 폴더에 error 로그와 warn 로그가 **둘 다** 출력되는 문제가 있었습니다. error가 warn보다 중요도가 높은 레벨이라 생긴 일입니다. 실 서버에서 같은 내용을 이유 없이 두 번 write하는 것은 부하가 되어, format에 filter를 주어 **자기 레벨에만 write**하도록 변경했습니다.

#### Redis 캐싱으로 800ms → 60ms

GitHub의 멘션에서 영감을 받아, 사용자의 follow/following 리스트를 전부 뽑아 클라이언트에 전달하고
클라이언트가 그 리스트로 멘션을 처리하는 형태로 만들었습니다.

- follow와 following을 각각 DB에서 읽어 set으로 중복을 제거해 하나의 리스트로 만들어야 했습니다.
- 둘은 서로 영향이 없어 비동기로 동시에 읽고 `Promise.all`로 묶어 시간을 줄였지만, **유저 1만 기준 300ms**가 걸렸습니다. 수가 늘면 더 오래 걸리고, 글 작성 페이지에 들어갈 때마다 기다려야 한다는 점이 흠이었습니다. 답글에서도 멘션 리스트를 쓰기 때문에 매번 요청하는 게 옳은지 의문이 들었습니다.
- 그래서 controller 단에서 **Redis에 캐싱**했습니다. 요청이 오면 Redis에 값이 있으면 그대로 돌려주고, 없으면 DB에서 읽어 Redis에 넣고 돌려줍니다.
- `CacheManager`를 기반으로 `CacheInterceptor`를 상속해, userId별 캐싱이 필요한 경우 key에 **url + userId**를 넣도록 오버라이딩했습니다. update가 발생하면 캐시를 지워야 하므로 **캐시 삭제 데코레이터**도 만들었습니다.
- 그 결과 멘션 리스트를 가져오는 시간이 두 번째 호출부터 **800ms → 60ms**로 줄었습니다.
