댓글·통계까지 전부 새로 붙였습니다.

옮기면서 검색해도 잘 안 나오는 함정을 여럿 밟았습니다. 그게 아까워서 시리즈로 남깁니다.
같은 길을 가려는 분이 저보다 덜 헤매면 좋겠습니다.

## 왜 옮겼나

티스토리도 글 쓰기에는 충분했습니다. 에디터도 편하고, 이미지도 알아서 올려줍니다.
그런데 두 가지가 계속 걸렸습니다.

### 마크다운으로 쓰고 싶었다

가장 큰 이유입니다. 코드와 표가 많은 글을 쓰다 보면 결국 마크다운이 편합니다.

티스토리에도 마크다운 모드가 있지만, 저장하는 순간 **HTML로 변환되어 보관**됩니다.
원본 마크다운은 남지 않습니다. 나중에 고치려고 열면 마크다운이 아니라 변환된 결과를
다시 손보게 됩니다.

이번에 옮기면서 그 흔적을 데이터로 확인했습니다. 제 글의 본문은 전부 이런 모양으로
저장돼 있었습니다.

```html
<p data-ke-size="size16">현업에서 서버를 Spring -&gt; Go로 ...<br />여기서 생겼던 ...</p>
```

더 재미있는 건 이겁니다. 어떤 글에서는 마크다운 링크를 붙여넣었더니,
그게 **`href` 속성 안으로 통째로 들어가** 있었습니다.

```html
<a href="%5Bhttps://github.com/golang/go/issues/3611%5D(https://github.com/...)">출처</a>
```

`[텍스트](주소)` 가 주소 자리에 그대로 박힌 겁니다. 그 글은 티스토리에서도
대괄호가 그대로 보이는 상태로 3년간 방치돼 있었습니다. 저는 모르고 있었고요.

지금은 글이 그냥 마크다운 파일입니다. 쓴 그대로 저장되고, 고칠 때도 그대로 열립니다.

### 콘텐츠가 내 저장소에 없었다

3년치 글이 남의 서비스 DB에만 있었습니다. 백업 기능이 있긴 하지만, 그건 백업이지
내가 다룰 수 있는 형태는 아닙니다.

지금은 전부 마크다운 파일로 git에 들어 있습니다. `grep`으로 찾고, 에디터로 고치고,
스크립트로 일괄 수정할 수 있습니다. 이 차이가 생각보다 큽니다.

실제로 이번 이전 작업에서, 84개 글의 코드블록 언어를 한 번에 바로잡고
깨진 링크를 찾아내는 일이 전부 스크립트로 끝났습니다. 플랫폼 안에서는
못 했을 일입니다.

## 무엇을 골랐나

`github.io`에 블로그를 올린다고 하면 선택지가 꽤 많습니다. 다만 **어느 쪽을 골라도
글은 마크다운 파일**이라, 위에서 말한 이유는 이미 해결됩니다. 그래서 기준은 다른 데
있었습니다. 이미 있는 글 84개를 얼마나 손 덜 대고 올릴 수 있느냐입니다.

| 엔진 | 대표 테마 | 특징 |
| --- | --- | --- |
| Jekyll | Chirpy, Minimal Mistakes | GitHub Pages가 기본 지원. 한국 개발자 블로그에 가장 흔함 |
| Hugo | PaperMod | 빌드가 압도적으로 빠름. 미니멀 |
| Astro | AstroPaper, Fuwari | 최신. 컴포넌트로 자유롭게 구성 가능 |
| Next.js | Tailwind Starter Blog | React 생태계. 설정이 가장 무거움 |

### 처음엔 Astro로 시작했다

Node만 있으면 되고, 콘텐츠 컬렉션으로 글과 프로젝트를 스키마까지 나눠 관리할 수 있어서
매력적이었습니다. 실제로 만들어서 배포까지 했습니다.

그런데 만들고 보니 **글 84개 · 카테고리 21종**을 감당할 UI를 처음부터 다 짜야 했습니다.
카테고리 트리, 태그 페이지, 아카이브, 검색, 목차(TOC), 다크모드 — 하나씩 만들다 보면
그게 곧 테마 하나를 만드는 일입니다.

### 결국 Chirpy로 갔다

Chirpy는 그 목록이 **전부 기본으로 들어 있습니다.**

- 좌측 사이드바에 카테고리 트리
- 태그 · 아카이브 페이지
- 글 내 검색
- 글마다 목차
- 라이트 / 다크 / 시스템 3단 테마 전환
- 2단계 카테고리 (`알고리즘/dp` 처럼)

특히 마지막이 결정적이었습니다. 티스토리 카테고리가 이미 `알고리즘/dp`, `Backend/go` 같은
2단계였는데, Chirpy가 정확히 같은 구조를 지원해서 **그대로 옮기면 끝**이었습니다.

흔한 게 단점이라면 단점입니다. 개발자 블로그를 돌아다니다 보면 "아, 저 테마" 하고
바로 알아봅니다. 그런데 흔한 데는 이유가 있더군요. 완성도가 높습니다.

> 이전 Astro 버전은 지우지 않고 `archive/astro` 브랜치에 남겨뒀습니다.
> 되돌릴 일이 생길지 몰라서인데, 덕분에 마음 편히 갈아엎을 수 있었습니다.
{: .prompt-tip }

## Claude Code와 같이 만들었다

이 작업은 처음부터 끝까지 [Claude Code](https://claude.com/claude-code)와 함께 했습니다.
"AI가 다 해줬다"는 이야기는 아니고, 역할이 꽤 명확하게 갈렸습니다.

**Claude가 잘한 것**

- 글 84개를 크롤링하고 HTML을 마크다운으로 바꾸는 변환기 작성
- 원문과 변환본을 **문장 단위로 대조**해 누락이 없는지 검증
- 테마 내부 코드를 읽고 "이 설정이 왜 안 먹는지" 근거를 찾아오는 일
- 배포 후 실제 브라우저로 열어 동작을 확인하는 일

**제가 해야 했던 것**

- 방향 결정 (Astro냐 Chirpy냐, 어떤 효과를 넣을지)
- 계정이 필요한 작업 (GitHub 앱 설치, 통계 서비스 가입, 2단계 인증)
- 결과물을 직접 눈으로 보고 "이건 아닌데" 하고 되돌리는 일

세 번째가 특히 중요했습니다. 중간에 몇 번, 그럴듯한 설명과 함께 **틀린 진단**이 나왔습니다.
"뒤 슬래시가 안 맞아서 그렇다" 같은 식으로요. 실제로 열어보고 아니라고 말해야 다시 팠습니다.

자세한 건 시리즈 마지막에 따로 정리하겠습니다.

## 최종 구조

```
namhyo01.github.io/
├── _config.yml          사이트 설정
├── _posts/              글 (마크다운)
├── _tabs/               사이드바 탭 (카테고리·태그·아카이브·포트폴리오·정보)
├── assets/img/posts/    글 이미지
├── tools/               빌드 전에 도는 스크립트
└── .github/workflows/   빌드 & 배포
```

`main`에 push하면 GitHub Actions가 빌드하고 배포합니다. 서버도, 결제도 없습니다.

여기까지가 선택의 기록입니다. 다음 글에서는 **실제로 글 84개를 옮기면서 만든 변환기**
이야기를 하겠습니다. 만료되는 이미지 URL, 엉터리 코드블록 언어, 제목 레벨 충돌 같은
것들을 어떻게 처리했는지 적겠습니다.
