- 문제: [153. Find Minimum in Rotated Sorted Array](https://leetcode.com/problems/find-minimum-in-rotated-sorted-array/)
- 난이도: Medium
- 언어: C++

## 문제

오름차순 정렬된 길이 `n` 배열을 `1`~`n` 번 회전시킨 결과가 주어진다.
예를 들어 `[0,1,2,4,5,6,7]` 은 이렇게 될 수 있다.

- `[4,5,6,7,0,1,2]` — 4번 회전
- `[0,1,2,4,5,6,7]` — 7번 회전 (**회전이 안 보인다**)

원소는 서로 다르다. 이 배열의 **최솟값**을 반환하면 된다.

> You must write an algorithm that runs in `O(log n)` time.

### 제약 조건

```
n == nums.length
1 <= n <= 5000
-5000 <= nums[i] <= 5000
All the integers of nums are unique.
```

### 예제

```
nums = [3,4,5,1,2]      ->  1
nums = [4,5,6,7,0,1,2]  ->  0
nums = [11,13,15,17]    ->  11
```

## 먼저 틀린 이야기부터

처음에 이렇게 냈다.

```cpp
return *min_element(nums.begin(), nums.end());
```

**답은 전부 맞는다.** 그리고 LeetCode 에 제출하면 **Accepted 가 나온다.**
제약이 `n <= 5000` 이라 전부 훑어도 0.002ms 에 끝나기 때문이다.

그런데 지문은 `O(log n)` 을 요구했고, 저건 `O(n)` 이다.

로컬 테스트 하네스에 `n = 10^7` 짜리 입력을 따로 넣어뒀더니 바로 걸렸다.

```
✓ n=1..60 의 모든 회전량 전수 확인
✓ 랜덤 테스트 300건 (n 최대 5000)
✗ n=10000000 이 14.84ms — 너무 느림 (배열을 전부 훑고 있을 가능성)
```

| n | 전부 훑기 | 절반씩 줄이기 |
| --- | --- | --- |
| 5,000 (제약 상한) | 0.002ms | 0.000ms |
| 10,000,000 | 14.84ms | 0.002ms |

**제약 안에서는 시간으로 구분이 안 된다.** 채점기가 통과시켜 준다고 요구사항을 지킨 게
아니라는 걸 눈으로 본 셈이다. 면접이면 여기서 갈린다.

## 접근

배열을 그려보면 구조가 바로 보인다.

```
값
 7 |       ●
 6 |     ●
 5 |   ●
 4 | ●
   |
 2 |             ●
 1 |           ●
 0 |         ●
   +---------------
     0 1 2 3 4 5 6   인덱스
```

**오름차순 계단 두 개**이고, 사이에 딱 한 번 뚝 떨어진다.
찾아야 할 최솟값은 그 **떨어진 직후**다.

그러면 `mid` 를 하나 집었을 때 **그게 위쪽 계단인지 아래쪽 계단인지**만 알면
나머지 절반을 통째로 버릴 수 있다.

### 어느 끝과 비교할 것인가

여기가 이 문제의 갈림길이다. `nums[mid]` 를 왼쪽 끝과 비교할지 오른쪽 끝과 비교할지.

`[11,13,15,17]` (회전이 안 보이는 입력) 에 둘 다 대입해 보면 답이 나온다.

```
[11, 13, 15, 17]
 lo   mid      hi     lo=0, mid=1, hi=3
```

- `nums[mid]=13` vs `nums[lo]=11` → `13 > 11` 이니 "오른쪽에 답이 있다" 로 판단.
  **틀렸다.** 답은 인덱스 0 이다.
- `nums[mid]=13` vs `nums[hi]=17` → `13 < 17` 이니 "왼쪽 절반에 답이 있다".
  **맞다.**

그래서 흔히 보는 정석 풀이는 오른쪽 끝과 비교한다.

## 내 코드 — 바깥 조건으로 예외를 걷어내기

나는 왼쪽 끝과 비교하는 형태로 짰다. 대신 **바깥에서 회전 여부를 먼저 본다.**

```cpp
class Solution {
public:
    int findMin(vector<int>& nums) {
        int left = 0;
        int right = nums.size() - 1;
        while (1){
            if (nums[left] > nums[right]){          // 이 구간이 회전돼 있는가
                int mid = (left + right) / 2;
                if (nums[left] > nums[mid]){
                    right = mid;                    // mid 가 아래쪽 계단 -> 답은 왼쪽
                }else{
                    left = mid + 1;                 // mid 가 위쪽 계단 -> 답은 오른쪽
                }
            }else{
                break;                              // 이미 정렬됨 -> nums[left] 가 답
            }
        }
        return nums[left];
    }
};
```

`nums[left] > nums[right]` 가 거짓이라는 건 **그 구간이 이미 정렬돼 있다**는 뜻이므로
`nums[left]` 가 곧 최솟값이다. 위에서 본 `[11,13,15,17]` 함정이 이 조건 하나로 사라진다.
왼쪽 끝과 비교해도 깨지지 않는 이유다.

종료도 보장된다. `left < right` 이면서 회전돼 있으면 `left <= mid < right` 이므로
`right = mid`(감소) 또는 `left = mid+1`(증가)로 구간이 반드시 줄고,
`left == right` 가 되면 바깥 조건이 거짓이 되어 멈춘다.

- **시간복잡도** `O(log n)`
- **공간복잡도** `O(1)`

## 두 형태를 재봤다

정석(오른쪽 끝 비교)과 비교했다. `n = 10^7`. 시간이 나노초 단위라 캐시 노이즈가 심해서
**배열 접근 횟수**로 쟀다. 두 구현이 `n=1..300` 의 모든 회전량에서 같은 답을 내는 것도
먼저 확인했다.

| 최솟값 위치 | 내 풀이 | 정석(오른쪽 끝 비교) |
| --- | --- | --- |
| 회전 없음 | **3회** | 49회 |
| 앞쪽 0.1% | 95회 | **47회** |
| 가운데 | **7회** | 49회 |
| 뒤쪽 99.9% | 95회 | **47회** |

갈리는 이유가 명확하다.

- 한 바퀴 도는 데 읽는 값이 **내 풀이는 3개**(`left`, `right`, `mid`),
  **정석은 2개**(`mid`, `hi`). 그래서 최악에서 약 2배 더 읽는다.
- 대신 내 풀이는 **구간이 정렬 상태가 되는 순간 즉시 빠져나온다.**
  최솟값이 가운데 근처면 몇 번 접는 것만으로 조건이 풀려서 7~11회에 끝난다.
  정석은 `lo == hi` 가 될 때까지 무조건 `log n` 번을 돈다.

둘 다 `O(log n)` 이고 상수만 다르다. **입력 분포에 따라 승자가 바뀐다.**

## 다시 볼 것

- **"정답이 맞다" 와 "요구된 복잡도를 지켰다" 는 다르다.**
  제약이 작으면 채점기는 통과시켜 준다. 지문에 복잡도 요구가 적혀 있으면 그게 문제의 일부다.
- `while (1) { if (조건) {...} else break; }` 는 `while (조건) {...}` 으로 바로 쓸 수 있다.
- `(left + right) / 2` 는 이 문제에선 안전하지만 `left + (right - left) / 2` 를 습관으로 들이는 게 낫다.
- `int right = nums.size() - 1;` 은 `size_t` → `int` 축소 변환이다. `n >= 1` 이라 안전하지만,
  빈 벡터였다면 `size() - 1` 이 거대한 값으로 감싼다.
