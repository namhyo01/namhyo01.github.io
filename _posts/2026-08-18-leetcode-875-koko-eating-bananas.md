LeetCode를 다시 풀기 시작했다. 유형을 미리 알면 훈련이 안 되므로,
문제만 받고 유형은 스스로 판별하는 방식으로 하고 있다.

- 문제: [875. Koko Eating Bananas](https://leetcode.com/problems/koko-eating-bananas/)
- 난이도: Medium
- 언어: Go

## 문제

코코 앞에 바나나 더미가 `n`개 있다. `piles[i]`는 `i`번째 더미의 바나나 개수고,
경비원이 `h`시간 뒤에 돌아온다.

코코는 **시간당 먹는 속도 `k`(양의 정수)를 미리 하나 정한다.** 그리고 매 시간마다

1. 더미를 하나 고르고
2. 그 더미에서 `k`개를 먹는다
3. 더미에 `k`개보다 적게 남아 있으면 남은 걸 전부 먹고, **그 시간에는 더 먹지 않는다**

3번이 이 문제 규칙의 전부다. 한 시간에 두 더미를 건드릴 수 없다는 뜻이다.
경비원이 돌아오기 전에 전부 먹을 수 있는 **최소 `k`** 를 구하면 된다.

### 제약 조건

```
1 <= piles.length <= 10^4
piles.length <= h <= 10^9
1 <= piles[i] <= 10^9
```

### 예제

```
piles = [3,6,7,11],      h = 8  ->  4
piles = [30,11,23,4,20], h = 5  ->  30
piles = [30,11,23,4,20], h = 6  ->  23
```

`k=4`면 3은 1시간, 6은 2시간, 7은 2시간, 11은 3시간 = 총 8시간으로 딱 맞는다.
`k=3`이면 1+2+3+4 = 10시간이라 초과다.

## 접근

`k`를 1부터 하나씩 올려보면 답은 **반드시** 나온다. 문제는 `piles[i]`가 최대 `10^9`이라
그렇게 하면 절대 안 끝난다는 것.

여기서 관찰해야 할 건 두 가지다.

**첫째, 속도가 `k`일 때 걸리는 시간을 바로 계산할 수 있다.**

$$\text{hours}(k) = \sum_{i} \left\lceil \frac{piles[i]}{k} \right\rceil$$

**둘째, `k`가 커지면 걸리는 시간은 줄어들기만 한다.** 왔다 갔다 하지 않는다.
즉 "h시간 안에 되는가?"라는 판정은 `k`에 대해 단조롭다.

```
k:      1    2    3   ...  22   23   24  ...  30
가능?   X    X    X   ...  X    O    O   ...  O
                                ^
                            여기가 답
```

X가 쭉 나오다가 O로 바뀌고 다시는 안 돌아온다. 그러면 그 경계를 이분탐색으로 찾으면 된다.
**배열에서 값을 찾는 이분탐색이 아니라, 답의 후보 범위를 이분탐색하는 것이다.**

탐색 범위는 `[1, max(piles)]`. 속도가 가장 큰 더미보다 커봐야 의미가 없기 때문이다.

## 코드

```go
func minEatingSpeed(piles []int, h int) int {
	slices.Sort(piles)
	st := 1
	num := len(piles) - 1
	end := piles[num]
	if num+1 == h {
		return end
	}
	for st <= end {
		mid := (st + end) / 2
		if howManyEatingHours(piles, mid) > h { // 시간 초과 => 현재 속도가 너무 느리다
			st = mid + 1
		} else {
			end = mid - 1
		}
	}

	return st
}

func howManyEatingHours(piles []int, c int) int {
	cnt := 0
	for _, pile := range piles {
		cnt += int(math.Ceil(float64(pile) / float64(c)))
	}
	return cnt
}
```

`st <= end`로 돌리고 끝나면 `st`를 반환하는 형태다. 조건을 만족하는 최솟값(lower bound)을
찾을 때 쓰는 관용구.

- **시간복잡도** `O(n log(max(piles)))`
- **공간복잡도** `O(1)`

## 해설

### 왜 이분탐색인가

"정렬된 배열에서 값 찾기"만 이분탐색이라고 생각하면 이 문제가 안 보인다.
이분탐색의 본질은 **판정이 단조로운 구간에서 경계를 찾는 것**이다.

그래서 이런 형태의 문제를 만나면 이 세 개를 세울 수 있는지 확인하면 된다.

1. 답의 후보 범위가 정수 구간으로 잡히는가 → `[1, max(piles)]`
2. 후보 하나를 주면 "가능/불가능"을 빠르게 판정할 수 있는가 → `hours(k) <= h`
3. 그 판정이 단조로운가 → `k`가 크면 시간은 줄기만 한다

세 개가 다 서면 이분탐색이다. "최소/최대 ~를 구하라"는 문제에서 자주 나온다.

### `math.Ceil` vs 정수 나눗셈

`(p + c - 1) / c`로 정수 연산을 하는 게 더 빠를 것 같아 바꿔봤는데, **재보니 반대였다.**

n=10^4 벤치마크:

| 구현 | ns/op |
| --- | --- |
| `math.Ceil(float64(p)/float64(c))` | **288,554** |
| `(p + c - 1) / c` | 636,658 |

부동소수점 쪽이 2.2배 빠르다. x86에서 64비트 정수 나눗셈(`DIV`)이 부동소수점
나눗셈(`DIVSD`)보다 느리기 때문이다. 정수 연산이 항상 빠르다는 건 착각이었다.

정밀도도 이 제약조건에서는 안전하다. `p/c`가 정수가 아니면 가장 가까운 정수와의 간격이
`1/c` 이상인데, float64의 절대 오차는 대략 `(p/c) × 1.1e-16`이라 `p < 9e15`이면 간격보다
작다. `p <= 10^9`이니 여유가 충분하다.

다만 제약이 커지면 깨지므로, 무조건 float을 쓰는 습관은 위험하다.

### 남은 것

- `if num+1 == h { return end }` 특수 케이스는 사실 불필요하다. 이분탐색이 알아서 찾는다.
  손으로 넣은 예외는 그만큼 틀릴 지점이 늘어난다.
- `slices.Sort(piles)`도 필요 없다. 이 알고리즘은 **최댓값 하나만** 있으면 되고,
  정렬은 호출자의 슬라이스를 뒤집어놓는 부작용까지 있다.
