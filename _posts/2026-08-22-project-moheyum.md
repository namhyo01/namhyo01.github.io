## 왜 만들었나

트위터와 인스타그램에서 영감을 받아, 글을 쓸 때 마크다운을 쓸 수 있다면 더 보기 좋은 글이
나오지 않을까 해서 만든 SNS입니다.

개발자 4명(BE 2, FE 2)으로 진행했고, 개발 기간 중 한 주씩 각 파트의 담당자 한 명씩을 교체해
양쪽 영역을 모두 개발했습니다.

## 토큰 기반 인증 처리

- access 토큰만 쓰기에는 보안 이슈가 있어 **refresh 토큰을 함께** 쓰기로 했습니다. 둘 다 쿠키에 담아 전달합니다.
- refresh 토큰은 in-memory인 **Redis에 저장**해 검증을 빠르게 했고, 유효 기간에 맞는 **TTL**을 넣어 관리했습니다.
- refresh 토큰을 쓰더라도 탈취당했을 때의 보안 이슈가 남아, **호출할 때마다 새로 발급**하도록 했습니다. 탈취당해도 최대 한 번만 쓸 수 있습니다.
- Express에서는 인증 절차를 전부 middleware로 처리했지만, NestJS에서는 역할을 분리해 **Guard**에서 처리하도록 했습니다.

## 이메일 인증 처리

회원가입과 비밀번호 찾기에 이메일 인증을 사용했습니다. `@nestjs-modules/mailer`와 네이버 아이디로 구현했습니다.

1. 서버가 임의의 6자리 코드를 만들고 암호화합니다
2. 암호화한 값은 쿠키로, 코드는 response로 클라이언트에 전달합니다
3. 클라이언트가 코드를 입력해 요청을 보내면, 쿠키의 값과 코드를 서버에 저장된 salt로 비교해 인증합니다

## 로깅

`nestjs-winston`과 `winston-daily-rotate-file`로 로깅을 담당했습니다.

- 처음에는 예외 처리가 각 서비스와 컨트롤러에 흩어져 있어 로그를 일일이 넣어야 했습니다. NestJS의 **exception filter**를 써서 예외 발생 시 필터가 로그를 남기도록 바꿨습니다.
- production 환경에서는 성능을 위해 console 출력을 하지 않고 file에 error와 warn만 남기도록 했습니다.

### 같은 로그가 두 번 쓰이던 문제

기존 방식에서는 warn 폴더에 error 로그와 warn 로그가 **둘 다** 출력되었습니다.
error가 warn보다 중요도가 높은 레벨이라 생긴 일입니다.

실 서버에서 같은 내용을 이유 없이 두 번 write하는 것은 부하가 됩니다.
format에 filter를 주어 **자기 레벨에만 write**하도록 변경했습니다.

## Redis 캐싱으로 800ms → 60ms

GitHub의 멘션에서 영감을 받아, 사용자의 follow/following 리스트를 전부 뽑아 클라이언트에 전달하고
클라이언트가 그 리스트로 멘션을 처리하는 형태로 만들었습니다.

### 문제

- follow와 following을 각각 DB에서 읽어 set으로 중복을 제거해 하나의 리스트로 만들어야 했습니다.
- 둘은 서로 영향이 없어 비동기로 동시에 읽고 `Promise.all`로 묶어 시간을 줄였지만, **유저 1만 기준 300ms**가 걸렸습니다.
- 수가 늘면 더 오래 걸리고, 글 작성 페이지에 들어갈 때마다 기다려야 한다는 점이 흠이었습니다. 답글에서도 멘션 리스트를 쓰기 때문에 매번 요청하는 게 옳은지 의문이 들었습니다.

### 해결

controller 단에서 **Redis에 캐싱**했습니다.

- 요청이 오면 Redis에 값이 있으면 그대로 돌려주고, 없으면 DB에서 읽어 Redis에 넣고 돌려줍니다.
- `CacheManager`를 기반으로 `CacheInterceptor`를 상속해, userId별 캐싱이 필요한 경우 key에 **url + userId**를 넣도록 오버라이딩했습니다.
- update가 발생하면 캐시를 지워야 하므로 **캐시 삭제 데코레이터**도 만들었습니다.

그 결과 멘션 리스트를 가져오는 시간이 두 번째 호출부터 **800ms → 60ms**로 줄었습니다.
