- 문제: [15. 3Sum](https://leetcode.com/problems/3sum/)
- 난이도: Medium
- 언어: Go

이 글은 **같은 문제를 두 번 푼 기록**이다.
8월 18일에 못 풀어서 해설을 봤고, 3일 뒤 아무것도 안 보고 다시 쳐서 통과했다.

풀이만 적으면 남는 게 별로 없다. 정작 다음에 도움이 되는 건
**"왜 처음에 못 풀었는가"** 쪽이라, 그 부분을 스스로 뜯어보는 데 절반을 썼다.

## 문제

정수 배열 `nums`에서 `nums[i] + nums[j] + nums[k] == 0`이 되는 모든 삼중항을 찾는다
(`i`, `j`, `k`는 서로 다른 인덱스). **답에 중복된 삼중항이 들어가면 안 된다.**

### 제약 조건

```
3 <= nums.length <= 3000
-10^5 <= nums[i] <= 10^5
```

### 예제

```
nums = [-1,0,1,2,-1,-4]  ->  [[-1,-1,2],[-1,0,1]]
nums = [0,1,1]           ->  []
nums = [0,0,0]           ->  [[0,0,0]]
```

## 첫 시도에서 막힌 곳

세 수를 전부 훑으면 `O(n^3)`이고 `n=3000`이면 안 된다는 건 알았다.
그래서 "하나를 고정하면 되지 않나?" 까지는 갔다.

그런데 거기서 이렇게 판단했다.

> 하나를 고정하는 데 `O(n)`, 남은 두 수를 찾는 데 `O(n^2)`니까 결국 `O(n^3)`.
> 개선이 없네.

**여기가 틀렸다.** 남은 문제는 "두 수의 합이 특정 값이 되는 쌍 찾기", 즉 Two Sum이고
**Two Sum은 `O(n)`에 풀린다.** 안쪽을 브루트포스로 잡아버려서
결론이 "개선 없음"으로 나왔고, 그래서 방향을 접었다.

`O(n) × O(n) = O(n^2)`. 앞에 붙는 정렬 `O(n log n)`은 흡수된다.

### 스스로 짚어보면

틀린 게 지식이 아니라 **습관**이었다. 아이디어(하나를 고정한다)는 이미 맞게 떠올렸는데,
그걸 검증하는 단계에서 안쪽을 "대충 다 훑겠지"로 계산하고 바로 기각해버렸다.

즉 **맞는 방향을 스스로 버린 것**이다. 몰라서 못 푼 것보다 이쪽이 더 아프다.

> 부분문제로 쪼갰으면, 그 부분문제의 **"최적" 복잡도**를 따져야 한다.
> 쪼개놓고 안쪽을 순진하게 계산하면 쪼갠 의미가 없어진다.

그리고 하나 더. "Two Sum이 `O(n)`" 은 사실 아는 내용이었는데도
3Sum 안에 들어와 있으니 연결이 안 됐다. 아는 걸 **다른 문맥에서 꺼내 쓰는 것**은
따로 훈련해야 하는 능력이라는 걸 이번에 알았다.

## 접근

### 1. 정렬

문제가 "순서는 상관없다"고 명시했다. 이 말은 **정렬해도 손해볼 게 없다**는 뜻이다.
그리고 정렬하면 두 가지가 공짜로 따라온다. 탐색 방법과, 이 문제의 진짜 난관인 중복 제거.

```
[-1, 0, 1, 2, -1, -4]  ->  [-4, -1, -1, 0, 1, 2]
```

### 2. 첫 수 고정 + 양끝 포인터

`nums[i]`를 고정하면 남은 구간에서 합이 `-nums[i]`인 두 수를 찾는 문제가 된다.
정렬돼 있으니 양끝에서 좁혀 들어가면 `O(n)`이다.

| 상태 | 행동 | 왜 |
| --- | --- | --- |
| `sum < 0` | `st++` | 더 커져야 하는데, 정렬돼 있으니 왼쪽을 올릴 수밖에 |
| `sum > 0` | `end--` | 더 작아져야 하니 오른쪽을 내림 |
| `sum == 0` | 기록 후 `st++` | 찾았다 |

**이게 왜 답을 안 놓치나.** `sum < 0`이라는 건 `nums[st]`가 현재 구간에서
**가장 큰 짝(`nums[end]`)과 붙여도 모자란다**는 뜻이다. 다른 어떤 짝을 줘도 더 작아지니
`nums[st]`는 영원히 가망이 없다. 그래서 버려도 안전하다.

### 3. 중복 제거 — 여기가 진짜

정답률이 낮은 이유가 거의 다 이것이다. 중복이 생기는 자리는 **딱 두 군데**다.

**(a) 고정하는 수가 같을 때**

```
[-4, -1, -1, 0, 1, 2]
      i=1  i=2   <- 둘 다 -1, 결과가 통째로 똑같이 나온다
```

`i > 0 && nums[i] == nums[i-1]`이면 건너뛴다. `i > 0` 조건이 붙는 이유는
`i == 0`은 비교할 이전 값이 없어서 무조건 살려야 하기 때문.

**(b) 정답을 찾은 직후 `st`를 옮길 때**

```
[-2, 0, 0, 2, 2]   (0,2)를 찾았는데
        st  end     st 옆에도 0, end 옆에도 2 -> 같은 답이 또 나온다
```

기록하고 `st++` 한 뒤, `nums[st] == nums[st-1]`인 동안 계속 전진시킨다.

**`end` 쪽은 건드릴 필요가 없다.** 고정값과 `st`가 정해지면 `end`는 자동으로
하나로 결정되기 때문이다.

`set`에 넣어 후처리하면 답은 맞지만, 면접에서는 감점 지점이다.

## 코드

```go
func threeSum(nums []int) [][]int {
	slices.Sort(nums)
	var res [][]int
	for i := 0; i < len(nums)-2; i++ {
		num := nums[i]
		if num > 0 { // 정렬돼 있으니 뒤는 전부 양수, 합 0 불가
			break
		}
		if i > 0 && num == nums[i-1] { // 중복 제거 (a)
			continue
		}

		st := i + 1
		end := len(nums) - 1
		for st < end {
			sum := num + nums[st] + nums[end]
			if sum == 0 {
				res = append(res, []int{num, nums[st], nums[end]})
				st++
				for st < end && nums[st] == nums[st-1] { // 중복 제거 (b)
					st++
				}
			} else if sum < 0 {
				st++
			} else {
				end--
			}
		}
	}

	return res
}
```

- **시간복잡도** `O(n^2)` — 정렬 `O(n log n)` + 바깥 루프 `n` × 투 포인터 `O(n)`
- **공간복잡도** `O(1)` — 정렬이 제자리, 출력 제외

## 해설

### 실측

n=3000에서 **9.1ms**. 세 수를 전부 훑는 풀이는 같은 입력에서 **1,038ms**로 100배 이상 차이다
(둘 다 삼중항 16,507개로 정답은 같다).

여기서 하나 배운 게 있다. 테스트 하네스에 성능 게이트를 걸 때 처음엔 10초로 잡았는데,
**`O(n^3)` 풀이가 1초에 끝나서 게이트 구실을 못 했다.** Go가 워낙 빨라서다.
파이썬 기준의 감각을 그대로 가져온 게 잘못이었다.

성능 임계값은 **정답 풀이와 순진한 풀이를 둘 다 재서** 그 사이에 잡아야 한다.
추측하면 틀린다.
