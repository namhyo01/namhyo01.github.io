- 문제: [128. Longest Consecutive Sequence](https://leetcode.com/problems/longest-consecutive-sequence/)
- 난이도: Medium
- 언어: C++

## 문제

정렬되지 않은 정수 배열 `nums` 에서 **값이 연속인** 원소들의 가장 긴 길이를 반환한다.

> You must write an algorithm that runs in `O(n)` time.

```
nums = [100,4,200,1,3,2]        -> 4    ([1,2,3,4])
nums = [0,3,7,2,5,8,4,6,0,1]    -> 9
```

배열에서 위치가 붙어 있을 필요는 없다. **값만 연속이면 된다.**
예제 1 에서 `1,2,3,4` 가 흩어져 있는 걸 보면 알 수 있다.

### 제약 조건

```
0 <= nums.length <= 10^5
-10^9 <= nums[i] <= 10^9
```

배열이 **비어 있을 수 있고**, 예제 2 를 보면 `0` 이 두 번 나온다 — **중복이 들어온다.**

## 접근

정렬하면 쉽다. 정렬하고 이웃끼리 이어지는지 세면 끝이다. 그런데 그건 `O(n log n)` 이라
지문의 요구를 어긴다.

정렬이 주는 게 뭔지 생각해보면, **"내 다음 값이 뭔지 안다"** 는 것이다.
그걸 정렬 없이 얻으려면 어떻게 해야 할까.

> 값 `x` 가 있을 때 **"`x+1` 이 존재하나?"** 를 상수 시간에 답할 수 있으면 된다.

DB 로 치면 **해시 인덱스**다. 범위 조회가 필요한 게 아니라 점 조회만 필요하니
B-tree 가 아니라 해시가 맞다. C++ 에서는 `unordered_set`.

### 그런데 이대로면 O(n²) 이다

집합에 다 넣고 각 원소에서 수열을 따라가면, `[1,2,3,...,n]` 같은 입력에서
1 에서 n 칸, 2 에서 n-1 칸, ... 이렇게 **같은 수열을 n 번 다시 걷는다.**

핵심은 **시작점에서만 걷는 것**이다.
`x` 가 수열의 시작이라는 건 **`x-1` 이 집합에 없다**는 뜻이다.

## 코드

```cpp
int longestConsecutive(vector<int>& nums) {
    unordered_set<int> um;
    int max_length = 0;

    for (const auto &num : nums ){
        um.insert(num);
    }

    for (const auto &num : um){
        if (!um.contains(num-1)) { // 이전 값이 없는가
            int current = num;
            int current_length = 1;
            while (um.contains(current+1)){ // 다음 값이 존재하면
                current++;
                current_length++;
            }
            max_length = max(max_length, current_length);
        }
    }
    return max_length;
}
```

- **시간복잡도** `O(n)`
- **공간복잡도** `O(n)`

### while 이 중첩돼 있는데 왜 O(n) 인가

겉보기엔 이중 루프라 `O(n²)` 같다. 그런데 **각 값은 while 안에서 평생 딱 한 번만 방문된다.**

`x` 가 while 로 방문됐다는 건 `x-1` 이 집합에 있다는 뜻이다.
그러면 `x` 는 바깥 `if (!um.contains(num-1))` 를 통과하지 못하므로
`x` 에서 새로 걷는 일이 없다.

즉 모든 while 실행 횟수를 다 더해도 `n` 을 넘지 않는다.

## 처음엔 틀렸다 — 순회 대상

첫 버전은 두 번째 루프를 `um` 이 아니라 **원본 `nums`** 에서 돌았다.
로컬 테스트는 통과했다. 그런데 이런 입력을 주면 무너진다.

```
nums = [1,1,1,...,1(5만개), 2,3,...,50000]
```

값 `1` 이 5만 번 나오는데 매번 `!um.contains(0)` 이 참이다.
그래서 **길이 5만짜리 수열을 5만 번 다시 걷는다.**

| 순회 대상 | 소요 |
| --- | --- |
| 원본 `nums` | **5,501ms** |
| 집합 `um` | **2ms** |

2,750 배. 고친 건 한 단어다.

```cpp
for (const auto &num : nums)   // 중복이 살아있는 원본
for (const auto &num : um)     // 중복이 이미 제거된 집합
```

`unordered_set` 이 중복을 합쳐주는데 정작 순회를 원본에서 해서 그 이점을 버린 셈이다.
DB 로 치면 인덱스를 잘 만들어놓고 `SELECT DISTINCT` 대신 원본 테이블을 풀스캔한 것.

> 로컬 하네스도 처음엔 이걸 못 잡았다. 성능 케이스를 `[1..n]` 셔플로만 만들어서
> **중복이 없었기 때문이다.** 중복이 많은 케이스를 따로 추가했다.
> 최악 입력을 만들 때 "무엇이 많으면 무너지는가" 를 축마다 따져봐야 한다.

## O(n) 요구가 뜻하는 것 — 정렬이 더 빠른데도

여기서 재밌는 걸 발견했다. `n` 을 키워가며 재봤다. 전부 `[1..n]` 을 섞은 배열.

| n | 집합 | 집합(`reserve`) | 정렬 |
| --- | --- | --- | --- |
| 10^5 | 6ms | 5ms | **4ms** |
| 10^6 | 148ms | 97ms | **50ms** |
| 5×10^6 | 1,435ms | 582ms | **281ms** |
| 10^7 | 3,291ms | 1,193ms | **574ms** |

**정렬이 계속 이긴다.** 그것도 격차가 **벌어진다** (1.5배 → 5.7배).

`unordered_set` 은 조회마다 해시를 계산하고 버킷 포인터를 따라가느라 캐시를 계속 놓친다.
정렬은 연속된 메모리를 순서대로 훑으니 캐시 친화적이다.
`reserve` 와 `max_load_factor` 로 재해싱을 없애도 절반만 회복된다.

그러니 지문의 `O(n)` 요구는 **"더 빠르게 만들라"가 아니다.**
이 규모에서는 정렬이 실측으로 빠르다.

요구하는 건 이거다.

> **정렬이 공짜로 주는 "순서" 라는 구조에 기대지 않고 풀 수 있는가?**

정렬은 강력한 도구지만, 그걸 못 쓰는 상황(스트리밍 입력, 정렬 불가능한 키,
입력을 변형하면 안 되는 경우)이 실무에는 얼마든지 있다.
그때 해시로 같은 답을 내는 방법을 아는지 보는 것이다.

점근 복잡도가 낮은 게 항상 빠르지 않다는 것도 같이 배운다.

해시맵이 최악 케이스에서만 이기고 균형 입력에서는 오히려 졌다.
