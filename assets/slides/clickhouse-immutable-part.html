PART 1

쿼리는 어떻게
빨라지나?

6단계 변환 · 옵티마이저 · Processor · 병렬성 · 정렬 키

PART 1 · 쿼리 실행

SQL은 6단계를 거쳐 실행된다

PART 1 · 옵티마이저

옵티마이저가 쿼리를 다시 쓴다

내가 쓴 쿼리

SELECT concat(lower('a'), upper('b')),
sum(a * 2)
FROM logs
WHERE (status = 1 OR status = 2
OR status = 3)
AND toYear(event_time) = 2025

25.8이 실제로 실행한 쿼리

SELECT 'aB',
sum(a) * 2
FROM logs
WHERE status IN (1, 2, 3)
AND event_time >= '2025-01-01'
AND event_time < '2026-01-01'

파란 두 줄이 핵심 — 범위 조건이 돼야 정렬 키 인덱스로 Granule을 건너뛴다.
OR가 2개면 IN으로 안 바뀐다(3개부터). EXPLAIN SYNTAX로는 안 보인다.

PART 1 · 실행 모델

한 행씩 부르지 않고 Block이 흐른다

PART 1 · 병렬성

병렬성은 데이터를 쪼개서 만든다

EXPLAIN PIPELINE · max_threads = 4

ExpressionTransform × 4
Resize 4 → 4
AggregatingTransform × 4
ExpressionTransform × 4
MergeTreeSelect × 4

데이터 주도 병렬성

Part · Mark 범위를 레인 4개에 나눠 같은 파이프라인 실행

부분 집계 → 최종 병합

레인별 로컬 해시 테이블 → 락 경합 대신 마지막에 합침

max_threads = auto(코어 수)

키우면 메모리 · 병합 비용과 다른 쿼리와의 CPU 경쟁도 커짐

PART 1 · 정렬 키 · 첫 번째 숫자의 답

정렬 키에 맞추면 아예 덜 읽는다

8,192행

ORDER BY event_time LIMIT 5

정렬 키 순서로 읽다가 5개 찾으면 멈춤 · Sort 단계 없음

100만 행

ORDER BY response_time LIMIT 5

전부 읽고 PartialSorting → MergeSorting → MergingSorted

optimize_read_in_order = 1 · optimize_aggregation_in_order = 0 (기본 꺼짐, 교재와 다름)

PART 2

데이터는 디스크에
어떻게 놓이나?

타입 = 파일 · Nullable과 LowCardinality · 코덱 · 계산 컬럼

PART 2 · 타입과 파일

타입을 고르면 파일이 정해진다

선언한 타입Part 안에 실제로 생긴 파일
Nullable(String)n.bin + n.null.bin (NULL 마스크)
LowCardinality(String)lc.bin + lc.dict.bin (사전)
Array(UInt16)arr.bin + arr.size0.bin (경계 오프셋)
Tuple(lat, lon)loc.lat.bin · loc.lon.bin (따로 읽기 가능)
Map(String, String)m.keys.bin · m.values.bin + m.size0.bin

min_bytes_for_wide_part = 0 으로 컬럼별 파일을 강제한 뒤 Part 폴더를 직접 확인

PART 2 · Nullable과 LowCardinality

Nullable은 비용, LowCardinality는 할인

Nullable: 파일 +1 · 정렬 키로 못 씀

LowCardinality: 국가 코드 적합 · 이메일 부적합

PART 2 · 코덱 · 세 번째 숫자의 답

값이 다 다르면 압축되지 않는다

PART 2 · 교재 정정

교재가 권장한 RLE 코덱은 없다

CREATE TABLE t (x UInt8 CODEC(RLE, LZ4)) ...

Code: 432. UNKNOWN_CODEC: Unknown codec family: RLE

25.8에 있는 코덱

LZ4 · LZ4HC · ZSTD · Delta · DoubleDelta · Gorilla · FPC · T64 · GCD · NONE

Gorilla “70~90% 절감”도

부드러운 곡선 Float에선 1.2배. 효과는 데이터 분포에 달려 있다

PART 3 · Part의 일생

PART 3 · Mutation · 두 번째 숫자의 답

UPDATE는 새 Part를 다시 쓰는 일

ALTER UPDATE · DELETE: 비동기, Part 단위 재작성

DELETE FROM: _row_exists 마스크만 (교재 밖)

PART 3 · DDL

가벼운 ALTER와 무거운 ALTER

ALTERPart 재작성확인한 결과
ADD COLUMN … DEFAULT없음메타데이터만
MODIFY COLUMN … CODEC없음새 Part부터 적용
MODIFY COLUMN 타입 변경있음all_1_1_0 → all_1_1_0_2
DROP COLUMN있음컬럼 파일 빠진 새 Part

무중단 DDL = 메타데이터 변경 → 앱 배포 → 신규 데이터 → 필요하면 백필 → 옛 컬럼 제거
