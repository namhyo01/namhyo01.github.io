PART 1 · 옵티마이저

옵티마이저가 쿼리를 다시 쓴다

내가 쓴 쿼리

SELECT concat(lower('a'), upper('b')),
sum(a * 2)
FROM logs
WHERE (status = 1 OR status = 2
OR status = 3)
AND toYear(event_time) = 2025

25.8이 실제로 실행한 쿼리

SELECT 'aB',
sum(a) * 2
FROM logs
WHERE status IN (1, 2, 3)
AND event_time >= '2025-01-01'
AND event_time < '2026-01-01'

파란 두 줄이 핵심 — 범위 조건이 돼야 정렬 키 인덱스로 Granule을 건너뛴다.
OR가 2개면 IN으로 안 바뀐다(3개부터). EXPLAIN SYNTAX로는 안 보인다.

PART 2 · 타입과 파일

선언한 타입Part 안에 실제로 생긴 파일

Q1 / 13 · PART 1 · 옵티마이저

정렬 키가 event_time일 때 WHERE toYear(event_time) = 2025는 인덱스를 쓸 수 있을까?

정답

쓸 수 있다

Analyzer가 event_time >= '2025-01-01' AND event_time < '2026-01-01' 범위로 바꾼다. toYear가 단조 함수라 역상이 연속 범위이기 때문 (optimize_time_filter_with_preimage)

Q2 / 13 · PART 1 · 정렬 키

정렬 키 (event_time, status), 100만 행. ORDER BY event_time LIMIT 5와 ORDER BY response_time LIMIT 5가 읽는 행 수는 몇 배 차이날까?

정답

약 120배

8,192행(Granule 1개) vs 1,000,000행. 앞은 정렬 순서로 읽다가 LIMIT에서 멈추고, 뒤는 전부 읽어서 정렬한다

Q9 / 13 · PART 3 · DDL

MODIFY COLUMN c CODEC(ZSTD(3))와 MODIFY COLUMN c Float64(타입 변경) 중 기존 Part를 다시 쓰는 것은?

타입 변경

Q10 / 13 · PART 3 · 파티션

거의 아니다
