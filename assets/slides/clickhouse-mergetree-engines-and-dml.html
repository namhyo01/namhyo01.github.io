PART 2 · 🔬 실측 · ReplacingMergeTree

중복은 언제 사라지고, 톰스톤은 언제 지워지나

CREATE TABLE r (id UInt64, ver UInt64,
               del UInt8, name String)
ENGINE = ReplacingMergeTree(ver, del)
ORDER BY id;

INSERT INTO r VALUES (1, 1, 0, 'v1');
INSERT INTO r VALUES (1, 2, 0, 'v2');
INSERT INTO r VALUES (2, 1, 0, 'x');
INSERT INTO r VALUES (2, 2, 1, 'x-deleted');
시점결과
INSERT 직후 count()⚠️ 4행 (아무것도 정리 안 됨)
FINAL 조회✅ (1, v2)만. id=2는 숨김
OPTIMIZE FINAL 후 일반 조회⚠️ (1, v2) + (2, x-deleted) — 톰스톤 남음
교재: 'is_deleted 행은 Merge 때 제거될 수 있다' → 25.8 기본값에선 안 지워진다. FINAL CLEANUP + 실험 설정 필요. 그래서 항상 FINAL로 읽어야 한다.

PART 2 · FINAL 운영

ReplacingMergeTree를 쓸 때 정해야 할 것

목표설계

PART 2 · 🔬 실측 · SummingMergeTree

숫자는 합쳐지고, 문자열은 하나만 남는다

CREATE TABLE sm (k UInt64, c UInt64, label String)
ENGINE = SummingMergeTree ORDER BY k;

INSERT INTO sm VALUES (1, 10, 'first');
INSERT INTO sm VALUES (1, 5, 'second');
OPTIMIZE TABLE sm FINAL;
SELECT * FROM sm;
kclabel
1✅ 15⚠️ 'first'
합칠 수 없는 값(uniq · 분위수 · 평균)이 필요하면 → AggregatingMergeTree + -State / -Merge.

PART 2 · 🔬 실측 · AggregatingMergeTree

상태를 저장하고, 조회할 때 합친다

-- 저장: quantilesState(0.5, 0.95)(x)

-- 교재 예제
SELECT quantilesMerge(q)(q) FROM ag;

-- 고친 버전
SELECT quantilesMerge(0.5, 0.95)(q) FROM ag;
쿼리결과

PART 3 · 🔬 실측 · Mutation

Mutation은 '전체 컬럼'을 다시 쓸까?

CREATE TABLE mu (k UInt64, a String, b String)
ENGINE = MergeTree ORDER BY k
SETTINGS min_bytes_for_wide_part = 0;

INSERT INTO mu SELECT number,
  toString(number), toString(number)
FROM numbers(1000);

ALTER TABLE mu UPDATE a = 'x' WHERE k = 1
SETTINGS mutations_sync = 1;

-- 새 Part all_1_1_0_2 에서
-- stat -c '%h %n' *.bin
파일하드링크 수의미
a.bin⚠️ 1새로 씀
b.bin✅ 2옛 Part와 공유
k.bin✅ 2옛 Part와 공유
교재: '전체 컬럼 파일을 다시 쓸 수 있다' → 실제는 바뀐 컬럼만. 그래도 1행 고치려고 그 Part의 a 컬럼 전체를 다시 쓴다.

PART 3 · 🔬 실측 · Lightweight

DELETE FROM과 UPDATE의 정체

DELETE FROM ld WHERE k < 3;
SELECT command FROM system.mutations;
-- (UPDATE _row_exists = 0 WHERE k < 3)
-- Part: all_1_1_0_2

UPDATE lu SET v = 'new' WHERE k = 1;
-- ❌ needs materialized _block_number column

CREATE TABLE lu2 (...) ENGINE = MergeTree ORDER BY k
SETTINGS enable_block_number_column = 1,
         enable_block_offset_column = 1;
UPDATE lu2 SET v = 'new' WHERE k = 1;   -- ✅
lu2의 Active Part행
all_1_1_05
patch-…-all_3_3_0_21
Lightweight DELETE = '마스크 컬럼을 쓰는 Mutation'. 디스크에서 즉시 사라지는 게 아니다 → 개인정보 파기는 Merge 완료까지 추적.

PART 3 · TTL

TTL은 삭제만 하는 게 아니다

TTL하는 일주의
… DELETE만료 행 제거Part 전체 만료일 때만 통째 삭제 (ttl_only_drop_parts = 0)
컬럼 TTL컬럼 값만 기본값으로빈 문자열 · 0이 '원래 값'과 헷갈림
RECOMPRESS CODEC(...)오래된 데이터 재압축CPU · Merge 비용
GROUP BY … SET …원본을 집계로 축소⚠️ GROUP BY 키 = 정렬 키 접두사여야 (아니면 BAD_TTL_EXPRESSION)
TO VOLUMEHot → Cold 이동⚠️ 교재 예시: XML 볼륨 cold ≠ DDL 's3_cold'
TTL은 별도 프로세스가 아니라 Merge에 붙어서 돈다. merge_with_ttl_timeout 기본 4시간 → 만료 즉시 사라지지 않는다.

PART 4 · 🔬 실측 · Part 폭증

작은 INSERT를 반복하면 결국 거부된다

CREATE TABLE tp (k UInt64) ENGINE = MergeTree
ORDER BY k
SETTINGS parts_to_throw_insert = 3,
         parts_to_delay_insert = 2;
SYSTEM STOP MERGES tp;

INSERT INTO tp VALUES (1);
INSERT INTO tp VALUES (2);
INSERT INTO tp VALUES (3);
INSERT INTO tp VALUES (4);
-- ❌ Code 252: Too many parts (3 ...).
--   Merges are processing significantly
--   slower than inserts. (TOO_MANY_PARTS)
설정 (25.8)기본값
parts_to_delay_insert1000 (파티션당)
parts_to_throw_insert3000 (파티션당)
max_parts_in_total100000 (테이블)
교재의 'Too many parts in all data parts'는 테이블 전체 한도 쪽 메시지. 실제로 먼저 만나는 건 파티션 단위 TOO_MANY_PARTS.

PART 4 · async_insert · 🔬 25.8 기본값

서버가 대신 모아 준다 — 교재와 다른 기본값

설정교재25.8 실제
async_insert—0 (꺼짐)
async_insert_max_data_size약 100KB ~ 1MB⚠️ 10 MiB
busy timeout200ms⚠️ 50~200ms 적응형 (use_adaptive_busy_timeout = 1)
async_insert_max_query_number—450 (쿼리 수로도 flush)
wait_for_async_insert—1 (flush까지 기다림)
wait_for_async_insert = 0이면 서버 재시작 때 버퍼 유실 가능. async_insert는 입력량이 Merge 처리량을 넘는 문제를 숨길 뿐 해결하지 않는다.

PART 4 · JOIN 알고리즘

오른쪽이 Build, 왼쪽이 Probe

join_algorithm동작언제
hash오른쪽 전체를 메모리 해시 테이블로오른쪽이 메모리에 들어감
parallel_hash해시 테이블을 쪼개 병렬 Build/Probe멀티코어 · 메모리 여유
grace_hash버킷으로 나눠 디스크 스필오른쪽이 메모리 초과
full_sorting_merge양쪽 정렬 후 병합아주 큼 · 이미 정렬
directDictionary / KV 직접 조회마스터 데이터
25.8 기본값 join_algorithm = 'direct,parallel_hash,hash', query_plan_join_swap_table = 'auto' → parallel_hash가 이미 기본이고, 작은 쪽을 자동으로 Build로 바꾼다.

PART 4 · 🔬 실측 · 2샤드 클러스터

샤딩 키가 다르면 정말 결과가 빠질까?

방식결과비용
데이터hits: 샤드1 {2,4} · 샤드2 {1,3}
users: 샤드1 {1,2} · 샤드2 {3,4}
일반 JOIN (25.8 기본)❌ 에러: distributed_product_mode = 'deny'—

교재: '각 샤드에서 로컬끼리 JOIN' → 25.8 기본값에선 실행 자체가 거부. 교재가 말한 동작(local)은 실제로 데이터를 잃는다.

PART 4 · 집계 콤비네이터

접미사 하나로 집계 동작을 바꾼다

접미사하는 일예
-If조건이 참인 행만countIf(status = 200)
-Array배열을 펼치지 않고 집계sumArray(prices)
-State / -Merge중간 상태 저장 / 합쳐서 최종 값uniqState → uniqMerge
-ForEach여러 행의 배열을 같은 위치끼리sumForEach(arr)
-Resample키 범위를 고정 구간으로avgResample(0, 86400, 3600)(v, key)

PART 4 · 🔬 실측 · 교재 예제

교재 예제 두 개는 그대로 쓰면 틀린다

SELECT sumForEach([1, 2, 3], [10, 20, 30]);
-- ❌ sum requires single argument

SELECT sumForEach(arr) FROM (
  SELECT [1, 2, 3] AS arr
  UNION ALL SELECT [10, 20, 30]);
-- ✅ [11, 22, 33]

SELECT avgResample(0, 86400, 3600)
       (latency, event_time) FROM logs;
-- ⚠️ [nan, nan, … nan]  24칸 전부
-- DateTime = 유닉스 초(약 17억) → 0~86400 밖
-ForEach는 행 사이 집계. -Resample은 키를 하루 시작 기준 상대 초로 바꿔야 24칸이 찬다.

PART 4 · 🔬 실측 · windowFunnel

30분 창, 20분 간격 3단계 — 몇 단계까지 갔을까?

INSERT INTO ev VALUES
  (1, '2026-08-26 10:00:00', 'A'),
  (1, '2026-08-26 10:20:00', 'B'),
  (1, '2026-08-26 10:40:00', 'C');

SELECT windowFunnel(1800)(t,
  e = 'A', e = 'B', e = 'C')
FROM ev GROUP BY uid;
해석예상
교재: 직전 단계 기준3
공식 문서: 첫 단계 기준2
25.8 실제2
창은 첫 조건을 만족한 시점부터 잰다. '30분 안에 결제까지' = 첫 조회 후 30분. 중복 · 같은 시각 처리 모드(strict_order 등)도 교재엔 없다.

PART 4 · 🔬 실측 · retention · ARRAY JOIN

결과가 조용히 0이 되거나 행이 사라진다

SELECT retention(0, 1, 1), retention(1, 0, 1);
-- [0, 0, 0]   [1, 0, 1]

SELECT id, x FROM (
  SELECT 1 id, [10, 20] a
  UNION ALL SELECT 2, []::Array(UInt8))
ARRAY JOIN a AS x;
-- (1, 10), (1, 20)         ← id = 2 사라짐

... LEFT ARRAY JOIN a AS x;
-- (1, 10), (1, 20), (2, 0)
retention r[i] = 첫 조건 AND i번째 조건. ARRAY JOIN은 빈 배열 행을 버린다 → 보존하려면 LEFT ARRAY JOIN. 배열 N개 → N행이라 비용도 N배.

Q1 / 11 · PART 2 · Replacing

정답

2

중복 정리는 Merge 또는 FINAL 때. UNIQUE 제약이 아니다.

Q2 / 11 · PART 2 · 톰스톤

정답

아니다

FINAL 조회에서 숨겨질 뿐 물리적으로 남는다. FINAL CLEANUP + 실험 설정 필요.

Q3 / 11 · PART 2 · Summing

SummingMergeTree에 (1, 10, 'first'), (1, 5, 'second')를 넣고 병합하면 label은?

정답

'first' 하나만

숫자만 15로 합산. 비숫자 컬럼은 하나만 남는다.

Q4 / 11 · PART 3 · Mutation

a.bin만

b.bin, k.bin은 하드링크로 공유. 그래도 Part의 a 컬럼 전체를 다시 쓴다.

Q5 / 11 · PART 3 · LWD

남는다

UPDATE _row_exists = 0 WHERE … Mutation으로 기록, Part 이름에 버전이 붙는다.

Q6 / 11 · PART 4 · 멱등성

2행

non_replicated_deduplication_window 기본 0. 켜야 1행.
